hisaab · agent tool safety for payments

An AI agent knew the amount was ₹1,50,000. It charged ₹15,000.

Razorpay's API takes amount in the currency's smallest unit — paise for INR. A developer reads that once. A language model re-derives it on every call, from what a merchant said out loud, and each slip is off by exactly the currency's multiplier. This is a measurement of how often that happens, and a runtime guard that catches it.

The premise

Success rate is the wrong unit when the tool is refund

Existing agent tool-call benchmarks — τ-bench, BFCL — score whether the task was completed. That question stops being interesting the moment the tool moves money. The right unit is rupees at risk, and reversibility.

The paise trap

To charge ₹500, a program must send 50000. Send 500 and it charges ₹5. Nothing errors. Nothing warns.

Indic amounts

sava lakh is 1,25,000. paune do hazaar is 1,750 — two thousand minus a quarter of a thousand. Two conversions in one breath, and the errors compound.

Attacker-writable text

Agents that answer chargebacks read dispute narratives and payment notes — fields the disputing party controls — while holding irreversible tools.

The conceptual spine

Agent frameworks treat every tool identically

fetch_payment and create_refund arrive at the model as two entries in the same JSON array, with the same weight, guarded by the same nothing. That is the actual bug. Naming the tiers is half the fix.

READ

No state change

A wrong answer, not a wrong outcome. fetch_payment

REVERSIBLE

Decays on its own

An unpaid link expires. create_payment_link

SEMI

Undone only at a cost

Reversing means a refund, and fees. capture_payment

TERMINAL

Money leaves. No undo.

create_refund · create_payout

An unclassified tool is TERMINAL. A new server release must not silently widen what an agent may do unsupervised. That default caught a real gap in this repo's own table — fetch_dispute was never registered, and fail-closed is why nothing unsafe happened.

The guard

Semantic and provenance-based, not policy-based

Spend caps and category allowlists answer “is this within budget?” — a policy question, well solved elsewhere. These are three questions a policy layer structurally cannot answer.

Unit sanity, against the utterance

A prior read bounds the ceiling; only the merchant's own words carry the intent. The guard parses the amount out of what was said and blocks a call that disagrees by exactly 100×.

This needs no prior read, so it fires on the very first tool call — and it caught every 100× error the model made.

Provenance tainting

Identifiers are tracked by where they were first seen: a human turn, a typed API field, or attacker-writable free text. Irreversible tools refuse the last kind.

Taint is sticky. A later clean sighting does not clear it — only a person naming it does.

Entity binding

The target must be an entity the conversation actually established. Right action, wrong customer is the failure no task-success metric can see, and it ran at 25.6%.

Readback in rupees

Irreversible calls are quoted back in the unit a human thinks in. A readback that repeats the model's own paise error back at someone is worthless.

What this does not do

The uncomfortable numbers, kept in

The BLOCK rules alone bought 4%

Modelled against an operator who approves whatever readback they are shown without reading it, the guard is nearly worthless. Everything else it does is convert a silent 100× error into a flagged one — worth a great deal, but only to someone who reads the flag. That operator has not been measured, and no stronger claim is made until they are.

Semantic amount errors cannot be blocked

paune do hazaar (1,750) misheard as do hazaar (2,000) is indistinguishable from an ordinary partial refund — both sit under the ceiling. Blocked 2 times out of 38, and that will not improve. They are surfaced with the discrepancy named, and a human decides. A guard claiming to block these would be lying about what it can see.

The corpus is one person's opinion until a second reads it

102 scenarios were hand-verified by their author. A blind annotation tool ships (hisaab.annotate) but the inter-annotator pass has not run, and the author cannot run it — whoever wrote the values already knows them. A further 130 machine-composed Indic scenarios ship verified: false and are excluded from every headline here.

One finding is withheld

A third finding — prompt injection reaching agents through merchant- and customer-authored free text — was run and produced a clear result against irreversible tools. It is not published here, and will not be until named contacts at Razorpay have seen it privately and a window is agreed.

Nothing was tested against any Razorpay-operated surface. The sandbox backend cannot express a refund or a payout by construction; the injection family is filtered out of it in code, and the simulator is the only target for adversarial work.

Method

What the harness found in itself

Seven defects in the guard, and three more that only appeared once real models and the real API were in the loop. Each is written up in full, because a defect in software published here gets described regardless of how it reads.

# The one that mattered most — found by a live run, not a test

# before: taint cleared if the id later appeared in a clean field
val in from_free_text and val not in (from_human | from_structured)

# The agent read a poisoned record, then called fetch_all_payments —
# an ordinary list call — and the flagged identifier came back exonerated.
# One innocent read defeated the whole provenance check. Agents make
# list calls constantly; no adversary effort is required.

# after: sticky, keyed to FIRST sighting. Only a person clears it.
provenance.get(val) == "free_text"

A truthiness trap

Verdict.__bool__ returned decision == ALLOW, so verdict.decision if verdict else ALLOW logged every block and confirmation as “allow” — in both runners. It would have silently emptied the false-positive column, which exists so the guard cannot win by refusing everything.

A metric that measured backwards

Rupees-at-risk counted only over-payment. Nearly every error was 100× under. On a refund that holds; on a payment link it is backwards, because a link for ₹1.25 instead of ₹125 is revenue that never arrives. It now branches on tool direction.

A simulator that lied politely

The sim returned {"items": []} for payment links where Razorpay returns {"payment_links": […]}. A simulator that normalises that away teaches an agent a response shape the real API never sends.

“Executed” meant two different things

It meant the guard permitted it, not the API accepted it. Identical against a simulator; not against reality, where one run permitted 39 calls and created 10 links. Rejected calls no longer inflate the headline.

The second deliverable

Six invariants, for a merchant integrating an agent

Written for someone shipping this, not for someone reading about it. Each states the failure it prevents, because an invariant nobody can picture failing does not survive its first sprint.

InvariantPrevents
Classify every tool by reversibility before exposing it The next release adding create_payout to your agent without anyone deciding it should be there.
Cross the unit boundary exactly once, in your code The model never seeing a paise field it is expected to fill.
Anchor every terminal call to a prior read A 100× slip surviving to the ledger. On a ₹50,000 order that is ₹50 lakh.
Identifiers carry provenance; free text cannot authorize A record the disputing party wrote deciding where your money goes.
Readback in rupees; refusal is the default A confirmation step faithfully echoing the model's own unit error back at someone who approves it.
Prefer the lowest tier that answers the question The agent inventing a second charge to refund — a well-formed call that is still wrong.
